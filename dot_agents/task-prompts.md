# タスクの依頼文

依頼文を作るときに、用途に合う例だけを使う。
短い修正なら「対象をどう変えるか」の一文でよく、すべての欄を埋める必要はない。
既知の文脈を使い、目的、対象、成功と判断できる結果を具体化する。
プロジェクトのコマンドや規約は AGENTS.md に置き、依頼文には今回だけの条件を書く。

## 実装・修正

```text
<対象>を、<入力・操作>のときに<期待する結果>になるように修正してください。
現状は<実際の結果>です。関連資料: <必要なファイル・issue>。
完了条件は<確認可能な挙動>です。実装、必要な動作確認、今回の変更に起因する失敗の修正まで進めてください。
<互換性や変更範囲など、今回固有の制約>を守ってください。
完了時に変更内容、検証結果、残る制約を報告してください。
```

実装の初稿で止めたい場合だけ、その時点での確認を指定する。
commit、push、PR作成まで依頼する場合は、含める変更と到達点を追記する。

## 調査

```text
<現象・疑問>を、<対象範囲>のコード・ログ・資料から調べてください。
知りたいのは<判断したいこと>です。
根拠付きで説明できるところまで調べ、事実と仮説を分けて、未解決なら不足する証拠を示してください。
調査結果と対応案の報告までを対象とします。
```

広い調査では、判断に必要な範囲や時間上限を追記する。
修正も求める場合は、上の実装・修正の完了条件を追加する。

## コードレビュー

```text
<PR URL・ブランチ差分・作業ツリー>をレビューしてください。
変更が導入する不具合と契約違反を、必要な呼び出し元や関連テストまで追って確認してください。
対象範囲のレビューを完了し、根拠のある指摘を重要度順に、発生条件とファイル・行番号付きで報告してください。
指摘がなければその旨と、確認範囲・検証できなかった点を示してください。
コード修正や外部へのコメント投稿は、この依頼には含めません。
```

対話形式で差分を読みたいときだけ、Hunkなどの表示方法と一度に進める範囲を指定する。

## 設計の相談

```text
<設計案・問い>について、<判断基準>を満たす方針を検討してください。
対象は<関連範囲>、合意済みの条件は<条件>です。
関連する既存実装・仕様を踏まえ、選択肢の利点と制約、推奨案、決定に必要な未解決事項を示してください。
<議論して合意する／指定ファイルに設計案をまとめる>ところまでを完了条件とします。
```

## PR作成まで進める

```text
<対象の変更>を確認してコミットし、現在の作業ブランチをpushしてドラフトPRを作成してください。
プロジェクトのベースブランチとPRテンプレートに従い、必要な検証結果を本文に記載してください。
対象外の変更は含めず、作成したPRの内容を確認してURLを報告してください。
```

## 定期監視

```text
<対象>の<確認する状態>を<頻度・期間>で監視してください。
前回から変化がない場合や対応不要の場合は通知せず、<意味のある変化・完了・失敗・要対応の条件>で通知してください。
通知には根拠と必要な次の対応を添えてください。
<終了条件>に達したら監視を終了してください。自動操作の範囲は<許可する操作>です。
```

監視の設定には、頻度だけでなく通知条件と終了条件も含める。
既存の通知方針を見直す場合は、その意図を引き継ぐ。
