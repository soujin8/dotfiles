# Git Commit

現在 git staging にある内容を元にして、コミットメッセージを作成する。

## 手順

1. `git status --short` で staging 済みのファイルを確認する。
   - staging が空の場合、未 staged の変更があれば「staging されていない変更がある」旨をユーザーに伝え、
     明示的な指示（対象ファイルの指定、または `git add` の許可）がない限り自分で staging しない。
     staging・未 staged いずれも変更がない場合はコミット対象がない旨を伝えて終了する。
2. `git diff --cached` で staged diff を読み、変更の意図と影響範囲を把握する。
3. staged されていない変更は、ユーザーから明示されない限りコミット対象に含めない。
4. staged diff に性質の異なる変更（例: 機能追加とフォーマット修正、無関係な複数ファイルの変更）が
   混在している場合は、無理に 1 つのメッセージにまとめず、その旨をユーザーに提示し
   コミットを分割すべきか確認する。
5. 差分の内容に基づいて、メッセージ方針に沿ったコミットメッセージを作成する。
6. ユーザーが明示的に「commit して」「commit まで実行して」等コミット実行を求めている場合のみ、
   そのメッセージで `git commit` を実行する。それ以外（「メッセージ作って」等）は
   メッセージを提案するだけに留め、`git commit` は実行しない。

### コミットメッセージの改行

- 本文に段落を含める場合は、シェルの ANSI-C quoting（例: `-m $'段落1\\n\\n段落2'`）などを使って、実際の改行を含む引数を渡す。
- `'段落1\\n\\n段落2'` や `"段落1\\n\\n段落2"` のような通常のクォートでは、`\\n` が文字列として保存されるため使わない。
- コミット後に `git show -s --format='%B' HEAD | sed -n 'l'` で確認し、本文に `\\n` が残っていれば、実際の改行で `git commit --amend` する。

## メッセージ方針

- 既存のリポジトリの慣習がある場合は `git log --oneline -20` 等で確認し、それに合わせる
  （言語、prefix 規約 `feat:` / `fix:` 等、絵文字の有無）。慣習が見当たらない場合は
  リポジトリ内の他のコミットメッセージと同じ言語（日本語 or 英語）を使う。
- 1 行目（件名）は 50 文字程度を目安に、変更内容を命令形または簡潔な説明で書く。
  末尾に句点は付けない。
- バグ修正、レビュー指摘への対応、互換性対応、設計変更、複数ファイルにまたがる変更では、
  件名だけで説明できる場合でも本文を必ず付ける。
- 本文はコードの変更内容を列挙するだけにせず、「なぜこの変更が必要になったのか」を中心に書く。
  少なくとも次の3点を含める。
  1. 背景・問題: 何が起きていたか、またはレビューで何が問題とされたか。画面上の挙動やユーザー影響が
     ある場合は、それも具体的に書く。
  2. 原因・判断: なぜその問題が起きたか、なぜ採用した実装方針で解決するのか。既存仕様・API互換性・
     legacy互換性など、別案を採用しなかった理由があれば明記する。
  3. 確認: 回帰テストや静的解析など、変更の妥当性を確認した方法を書く。
- 本文の説明は、現在の会話、レビューコメント、Issue、設計資料、差分から根拠を得る。根拠のない背景を
  推測で補わない。必要な背景が確認できず、コミットの意図を説明できない場合はコミット前にユーザーへ確認する。
- 本文は通常、背景・原因と判断・確認を段落または箇条書きで2〜4段落にまとめる。単なるファイル一覧や
  「〇〇を修正した」という変更内容の言い換えだけで終わらせない。
- 差分から意図が読み取れない場合は、推測で確定せずユーザーに確認する。
