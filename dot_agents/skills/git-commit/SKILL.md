# Git Commit

## 対象と実行範囲

- `git status --short` と `git diff --cached` で staged の内容を確認する。メッセージだけの依頼ではコミットしない。
- staged の内容を指定された場合は、その範囲を守る。「この変更をコミットして」など対象が会話から明確な場合は、該当する変更の staging も依頼に含めて進める。
- 対象外のユーザー変更を混ぜない。staged が空で対象も特定できない場合は、変更を確認してから必要な範囲だけ質問する。
- 性質の異なる変更が混在していても、ユーザーがまとめてコミットする範囲を指定済みなら従う。対象の境界が不明な場合に確認する。

## メッセージ

- リポジトリの言語や prefix の慣習に合わせる。件名は変更の要点を簡潔に述べ、末尾に句点を付けない。
- バグ修正、レビュー対応、互換性対応、設計変更では、背景や判断を本文に残す。内容のある一段落で足りる場合は、固定の段落数や見出しを増やさない。
- 背景は会話、Issue、レビュー、資料、差分から得る。根拠がない作者の意図を補わず、確認できる変更と理由だけを書く。
- 本文は実際の改行を含む一時ファイルへ書き、`git commit -F <file>` で渡す。

コミットを依頼されていれば実行し、結果と作業ツリーを確認する。フックの失敗は原因を確認し、今回の変更による失敗を修正する。フックの無効化や無関係な修正で通さない。完了時はコミットIDと要点を伝える。
