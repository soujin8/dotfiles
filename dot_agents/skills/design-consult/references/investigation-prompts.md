# 調査プロンプト テンプレート集

`design-consult` スキルの手順3（3リポジトリ並列調査）で使う Explore サブエージェント向けプロンプトのフル例文。
SKILL.md 本体には型だけを書き、実例はここにまとめる。テーマに応じて調査項目を差し替えて使うこと。

## 共通の型

各リポジトリごとに、以下の4パーツで構成する。

1. **冒頭**: 「調査対象: `<パス>` （`<説明>`。まず README / AGENTS.md を読んで構成を把握すること）」
2. **目的文**: 「『`<テーマ>`』設計レビューのための現状把握。以下を very thorough に調査して報告せよ。」
3. **番号付き調査項目**: テーマに応じて生成する。観点の引き出しとしては以下を使う。
   - エンドポイント/ルーティング定義とハンドラの場所
   - 処理フロー（どのタイミングで何を保存・呼び出すか）
   - 状態遷移（どこでどう更新するか）
   - 重複実行対策（CAS? UPDATE WHERE? ロック? 具体的な SQL/コードを引用させる）
   - エラー処理・タイムアウト・リトライ・失敗時の状態遷移（stuck 防止、中間状態が残る可能性）
   - エッジケースの扱い（データなし、対象外、想定外入力）
   - データ保存（どのテーブル・カラムに何を書くか）
   - 外部API呼び出し（呼び出し箇所、失敗時の扱い）
4. **末尾の報告形式指定**（固定文言、変更しない）:
   > 報告形式: 各項目について、ファイルパス:行番号つきで事実を列挙。推測は「推測」と明記。コード引用は要点のみ短く。

## 実例: assessment-api（Rust 賃料査定API）向け

テーマ例: 「査定結果画面の賃料最速表示」設計レビュー。

```
調査対象: /home/h-mochizuki/dev/github.com/developers-terminal/assessment-api
（Rust製の賃料査定API。まず README / AGENTS.md を読んで構成を把握すること）

「査定結果画面の賃料最速表示」設計レビューのための現状把握。以下を very thorough に調査して報告せよ。

1. 既存エンドポイント一覧（特に /v1/assessments, /v1/assessments/async 等）。ルーティング定義ファイルとハンドラの場所。
2. /v1/assessments/async の処理フロー: pending レコード作成時に何を保存するか、worker がどう起動され、どこで賃料計算・類似事例検索・ds-api 呼び出し・保存を行うか。
3. 重複実行対策の実装（CAS? UPDATE WHERE? ロック?）。具体的な SQL/コードを引用。
4. 状態遷移をどこでどう更新しているか。
5. エッジケース（事例なし、unassessable）の扱い。
6. comparison_approach（類似事例比較）のロジックがどこにあり、何を入力・出力とするか。
7. assessments テーブルのスキーマと、rooms 保存に関する処理。
8. ds-api（外部MLモデルAPI）呼び出し箇所、リクエスト/レスポンス形式、失敗時のフォールバック有無。
9. タイムアウト・リトライ・失敗時の状態遷移（stuck 防止）。worker クラッシュ時に中間状態が残る可能性。

報告形式: 各項目について、ファイルパス:行番号つきで事実を列挙。推測は「推測」と明記。コード引用は要点のみ短く。
```

## ds-api（MLモデルAPI）について

ds-api / model.sumasate.jp は直接コードを読めない（別リポジトリで手元に無い、またはアクセス不可）。
real_estimator・assessment-api の AGENTS.md や、呼び出し元コードのコメント・リクエスト/レスポンス定義から
仕様を推測する。断定できない場合は「推測」「要ヒアリング」と明記し、独立した調査項目として本体が直接確認する
か、レビューmdの「5. 追加で確認すべき質問」に回す。
