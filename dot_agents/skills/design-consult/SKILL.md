# Design Consult

不動産賃料査定サービスの設計相談を、根拠付きレビューmdとしてまとめるための定型儀式。
思いつきで答えず、必ず実コードで裏取りしてから意見を出す。

## 前提: 対象リポジトリ

- assessment-api（Rust 賃料査定API）: `/home/h-mochizuki/dev/github.com/developers-terminal/assessment-api`
- real_estimator（Rails モジュラモノリス）: `/home/h-mochizuki/dev/github.com/developers-terminal/real_estimator`
- フロントエンド（React/TS）: `real_estimator/app/javascript` 配下
- ds-api / model.sumasate.jp（MLモデルAPI）: 直接コードは見られない。各リポジトリの AGENTS.md 経由で参照する

これらはリモート ssh 環境上のパス。パスが存在しない環境（ローカル等）で発動した場合は、
勝手に別パスを推測せず、対象リポジトリの場所をユーザーに確認してから進める。

## 手順

1. **wiki を参照する**（wiki スキルに委譲）。`~/wiki/INDEX.md` を読み、テーマに関連するページ（査定フロー、
   comparison_approach、assessments テーブル、rooms保存など）があれば中身も読む。相談テーマを一言で表した
   args を渡す。例: 「査定結果画面の賃料最速表示設計レビュー。assessment-api / real_estimator / ds-api の
   査定フロー、comparison_approach、assessments テーブル、rooms保存に関する知識を参照したい」
2. **議論用mdを読む**。ユーザーが `@` で添付した discussion-prompt.md（および baseline.md / design.md があれば
   それも）を読む。discussion-prompt.md の想定構成は次の通り: `## 目的` / `## 現時点の合意方針`（「一旦合意済み
   として扱う。ただし重大な設計欠陥があれば指摘」の前提つき）/ `## 特に議論したい未決定事項`（番号付き）/
   `## レビュー時の期待アウトプット` / `## 制約` / `## 参照ファイル`。
   discussion-prompt.md が用意されていない場合は、mdの事前作成を強制せず、口頭の相談内容から
   未決定事項を聞き出して進めてよい。
3. **3リポジトリを Explore サブエージェントで並列調査する**。メインの会話コンテキストを汚さないために、
   コードの実地調査は必ずサブエージェントに投げる。assessment-api / real_estimator / フロントエンドの3つを
   同一メッセージ内で並列起動する（依存が無いので同時に投げる）。プロンプトの型と実例は
   `references/investigation-prompts.md` を読んで作成すること。プロンプトは必ず次の要素を含める:
   - 冒頭: 調査対象パスと一言説明、「まず README / AGENTS.md を読んで構成を把握すること」
   - 目的文: 「『<テーマ>』設計レビューのための現状把握。以下を very thorough に調査して報告せよ。」
   - テーマに応じた番号付き調査項目（エンドポイント/処理フロー/状態遷移/重複実行対策/エラー処理/
     データ保存/外部API呼び出し等の観点から生成する）
   - 末尾に固定文言: 「報告形式: 各項目について、ファイルパス:行番号つきで事実を列挙。推測は「推測」と
     明記。コード引用は要点のみ短く。」
4. **本体が要所を直接裏取りする**。サブエージェントの報告を鵜呑みにせず、レビューの結論を左右する重要箇所
   （懸念の根拠になる行、状態遷移の分岐点など）は Read/grep で自分の目で確認する。サブエージェント間で
   矛盾する報告があれば、ここで解消する。
5. **レビューmdを出力する**。出力構造は下記「レビューmdのテンプレート」に固定する。ユーザーが discussion-
   prompt.md を用意していた場合、ファイル名は揃える: `assessment-result-<テーマ>-review.md` を
   `/home/h-mochizuki/dev/github.com/developers-terminal/` 直下に置く（他の3点セットと同じ場所）。
   相談が口頭ベースだった場合はファイル出力を強制せず、チャット上でこの構造のまま回答してよい。
6. **wikiへの書き戻しを提案する**。レビューの結論、特に「なぜその設計にしたか」という背景は、コードを
   読むだけでは復元できない知識になる。レビューmd出力後、wiki スキルに委譲して該当ページ（無ければ新規）へ
   の反映をユーザーに一言提案する。強制的に書き戻さない — 提案に留め、実行はユーザーの意思を確認する。

## レビューmdのテンプレート

見出し構造は固定する。テーマ・懸念の数に応じて中身は変わってよいが、見出しの型は崩さない。

```markdown
# <テーマ> 設計レビュー

作成日: <日付>
レビュー対象ファイル: <discussion-prompt.md 等へのパス、または「口頭相談」>
根拠: 実コード調査（assessment-api / real_estimator / フロントエンド を Explore で並列調査 + 本体で裏取り）

## 1. 重大な懸念

### 懸念A: <影響を見出しに明記。バグ・不整合・課金影響・データ破壊・ユーザー影響を優先して並べる>

## 2. 未決定事項への推奨回答

（入力mdの「特に議論したい未決定事項」の番号と対応させて回答する）

## 3. 状態遷移案

## 4. 実装分割案

### assessment-api
### Rails
### フロントエンド
### テスト方針

## 5. 追加で確認すべき質問（優先度順）
```

## 原則

- 調査はサブエージェント、判断は本体。コードを読んだ「量」をコンテキストに溜めず、要点だけ本体に残す。
- 推測と事実を混同しない。サブエージェントにも本体にも「推測」は明記させる。
- 「1. 重大な懸念」は必ずユーザー影響・データ破壊・課金影響の順で優先度をつける。単なる好みや美観の指摘を
  紛れ込ませない。
- discussion-prompt.md の「現時点の合意方針」は基本尊重する。覆すのは重大な設計欠陥を見つけた場合のみで、
  その根拠は必ずファイルパス:行番号で示す。
