# モジュール設計レビュー

Vlad Khononov『ソフトウェア設計の結合バランス 持続可能な成長を支えるモジュール化の原則』を判断の基礎にする。
目的は、想定する変更を適切な境界に閉じ込め、理解と変更に必要な労力を減らすこと。
結合の最小化やモジュール数の増加を目標にしない。
強く関連するものを近づける判断と、関連の薄いものを分ける判断の両方を行う。

書籍の判断モデルと出典は [references/coupling-model.md](references/coupling-model.md) にある。
分類時は「統合強度」、境界の評価時は「距離」「変動性」「均衡の判断」、提案時は「再均衡化」を参照する。
原本PDFが手元になくても、このスキルと参照資料だけでレビューできる。
証拠の集め方と報告形式は、書籍を実務のレビューへ適用するための手順である。

## 対象と比較の単位

- 指定されたPR、コミット範囲、ファイル、設計案を対象にする。指定がなければ、まず作業ツリーとステージ済みの差分を確認する。どちらもなければ対象を確認し、任意の過去コミットに置き換えない。
- 関数、クラス、パッケージ、サービスのどの境界を評価しているかを明示する。同じ対象でも、内部の凝集と外部への結合を分けて見る。
- 差分では、変更前後で共有知識、距離、変動性のどれが変わったかを比較する。既存の課題を今回導入された問題として報告しない。
- レビューだけの依頼では、コード修正や外部へのコメント投稿を行わない。修正も依頼されていれば、その範囲で続ける。

## 証拠を集める

対象の目的と公開する機能を読み、呼び出し元と依存先、共有する型やデータ、関連テストや仕様を必要な範囲まで追う。
境界の名前ではなく、利用側が知る必要のある実装詳細、ルール、状態、順序に注目する。
認可済みであることや実行環境など、公開操作に表れない利用上の前提も確認する。
importや直接呼び出しがなくても、同じ業務ルールの重複、イベント形式、共有DB、設定値、処理順序から関係を探す。

主要な関係ごとに、次を整理する。小さなレビューではメモでよく、一覧表の作成は必須ではない。

| 観点 | 記録する内容 |
| --- | --- |
| 境界と知識 | 何がどこに隠され、誰が何を知るか。公開契約と実装詳細の区別 |
| 統合強度 | 侵入・機能・モデル・コントラクトのどれか。その分類を裏づける利用箇所 |
| 距離 | モジュール階層、所有者、実装・テスト・リリースの単位。共同変更の調整コスト |
| 変動性 | 共有される知識が変わる理由と見込み。上流から強制される変更も含む |
| 変更の波及 | 具体的な変更を加えたとき、何を一緒に直す必要があるか |

知識の流れは通常、依存の矢印と逆になる。
機能結合では双方が共有ルールを持つため、一方だけを変更の起点と決めつけない。
変動性には仕様や変更計画、関連する履歴の内容を使う。
履歴を使う場合は対象と期間を示し、コミット件数や同時編集だけから高変動や共同変更の必然性を断定しない。
チーム構成や将来の変更予定をコードの配置や名称から推測して事実扱いしない。

## 判断する

1. **境界は知識を隠しているか。** 公開インターフェイスだけで利用できるか、利用側が内部モデルや手順を再現していないかを見る。薄いラッパーや同形DTOを置いただけでは、独立して変更できる証拠にならない。
2. **一緒に変えるものが離れていないか。** 順序、原子性、一貫性、同じルールの複数実装を確認する。必要な強い結合は認め、その知識を近い境界に集める選択肢を検討する。
3. **別々に変えるものを閉じ込めていないか。** 同じクラスや機能モジュールに無関係な変更理由を集め、理解やテスト、リリースを不要に共有していないかを見る。同じフォルダにあるだけでは指摘しない。
4. **距離と変動性に見合う強度か。** 遠くて頻繁に変わる知識への強い依存を優先して調べる。安定した共有モデルを一律に問題視せず、変更要求が不明なら不明とする。
5. **提案で何の負担が変わるか。** 知識の非公開化、契約の限定、機能の移動、統合、分割、現状維持から、問題を解く最小の案を選ぶ。追加される変換、抽象化、互換性維持、実行時依存と、上位モジュールへの影響も比較する。

指摘する前に、具体的な変更シナリオと波及先で因果関係を確認する。
要件や履歴から支持される変更と、説明用の仮定を区別する。
将来あり得るというだけの変更を理由に抽象化を求めない。
設計パターン名、ファイルの大きさ、依存数、単一の点数だけでは問題と判定しない。
同じデータベース、非同期通信、共通インターフェイス、似たコードは調査の手がかりであり、結論ではない。

## 報告する

対象と評価する境界を短く示し、根拠のある指摘を影響の大きい順に報告する。
指摘には次を含める。定型欄を埋めるために同じ説明を繰り返す必要はない。

- **場所と関係**：ファイルと行番号、関係するモジュール。設計案なら文書の節や図の要素を使う。
- **観察と影響**：何の知識を共有し、どの変更がどこへ波及するか。強度、距離、変動性の根拠を添える。
- **提案と代償**：どの境界をどう変え、何を隠すか。減る負担と増える負担を示す。
- **確認方法**：変更の局所性、公開契約、原子性など、提案の効果を確かめる具体的な方法。

重要度は影響から決める。要件上の整合性や独立リリースが成立しない問題を高く、根拠のある反復的な変更負担を次に扱う。
推測だけの懸念は確定指摘と分け、判断に不足する証拠を添える。
指摘がなければその旨と確認範囲を述べる。現状維持が妥当な理由や、再評価すべき条件があれば短く示す。
テストを実行した事実、コードから確認した事実、未検証の推定を区別する。
