# 結合バランスの判断モデル

## 出典と読み方

Vlad Khononov『ソフトウェア設計の結合バランス 持続可能な成長を支えるモジュール化の原則』（インプレス、日本語版）。
原著は *Balancing Coupling in Software Design*。
以下はレビューに必要な考え方の要約と適用であり、原文の転載ではない。
節ごとの「書籍」は概念の根拠、「レビューへの適用」はその概念を証拠のある指摘へ変えるための手引きを示す。
ページ番号は日本語版の印刷ページ。作成時の312ページのPDFでは、本文の印刷ページに28を足した値がPDFの1始まりのページ番号となる。

## モジュールが隠す知識

書籍：4.3〜4.4、pp.57–68；7.6.3、pp.133–135。

モジュールは公開する機能と、その実現に必要なロジックを分ける。
さらに、実行環境や事前の認可など、動作するコンテキストについての前提を持つ。
抽象化は利用する文脈に必要な情報を残し、それ以外を隠す。
利用側が少ない知識で複雑な仕事を頼める「深いモジュール」は、理解しなければならない範囲を縮める。
一方、細分化によって接続や理解すべき要素が増えれば、複雑性がモジュールの内側から外側へ移っただけになる。

レビューへの適用：

- 利用側に必要な準備、引数の意味、呼び出し順序、例外処理まで含めて、公開インターフェイスの負担を見る。
- 一貫性やトランザクションの意味など、正しく使うために必要な情報まで隠していないかを確認する。
- 「どの内部変更をしても利用側を変えなくてよいか」で、隠せた知識を説明する。
- 内部データを鏡写しにしたDTO、単なる転送メソッド、利用側に手順を組み立てさせる分割は、実際の独立性を調べる。名称や別ファイル化だけで成功と判定しない。
- 同形DTOにも契約を独立して維持する意味があり得る。現在の形が同じという理由だけで削除を勧めない。
- 深さをコード行数やメソッド数の比率で採点しない。統合後に無関係な知識まで集めていないかも確認する。

## 統合強度

書籍：7.2〜7.8、pp.115–141。
強度は境界を越えて共有する知識の種類と範囲を表す。
弱い順にコントラクト結合、モデル結合、機能結合、侵入結合となる。
関係ごとに評価し、複数の種類の知識がある場合は一つの弱い分類で強い関係を隠さない。

| 分類 | 書籍の区別 | レビューで確かめること |
| --- | --- | --- |
| コントラクト結合 | 通信に必要な知識へ絞った統合専用モデルや操作・プロトコルを共有する。内部の変化を境界で吸収できる | 利用側が何を必要とするか。内部変更後も同じ契約を維持できる変換や責務があるか |
| モデル結合 | 機能の実装に使うドメインのデータモデルを境界越しに共有する | 内部の型、構造、意味の変更が利用側へ伝わるか。モデルを使う目的が双方で異ならないか |
| 機能結合 | 関連した振る舞いや業務ルールを共有し、一緒に変更・実行する制約がある | 必須の処理順序、整合性、同じルールの複数実装。直接の参照がない関係も追う |
| 侵入結合 | 統合に使うことを意図していない実装詳細に依存する | 非公開メンバー、内部DBや内部イベント等への依存が、提供側の意図する契約を迂回していないか |

コントラクトは、新設のDTOに限らない。内部の手順を隠す公開メソッドや既存の通信プロトコルでも成立する（7.6.1、pp.131–132）。
公開された機能を呼ぶだけで、機能結合とは判定しない。業務ルールや順序・整合性の判断を双方が分担しているかを確認する。

### 機能結合の内訳

書籍：7.4、pp.118–122。

- **シーケンシャル機能結合**：正しさのために複数操作の順番やタイミングを共有する。
- **トランザクション機能結合**：複数操作が一つの作業単位を構成する。値の整合性や、同じ整合したデータを扱う必要がある。
- **対称機能結合**：同じ機能の複数実装を、要件変更時に一緒に更新しないと不整合になる。実装の見た目やアルゴリズムが異なっていても成立する。

レビューへの適用：

同じ形のコードが別の業務上の理由で独立して変わるなら、重複だけから対称機能結合としない。
逆に、別言語や別方式で同じ判断を再実装していても、その結果を一致させる要件があれば関係を見落とさない。
原子性が必要な処理を非同期化するだけでは制約は消えない。
共有ルールの所有者、全操作の成功・失敗条件、許される不整合の範囲を先に確認する。

### 通信方式と知識を分ける

書籍：7.2.1、p.116；7.3.1〜7.3.2、p.117；7.4.3、pp.121–122；7.5.2、pp.126–127；7.6.4、pp.135–136；7.8、pp.139–140。

同じDBを使う設計でも、意図しない内部アクセスは侵入結合、共有データへの協調更新は機能結合、意図して公開した内部データモデルの参照はモデル結合、独立した統合用スキーマはコントラクト結合になり得る。
意図して使うORMのリフレクションを、構文だけで侵入結合としない。
公開APIであっても内部モデルや業務上の制約を共有していれば、その知識に応じた強度になる。

同期から非同期へ変えても、同じ知識を共有する限り統合強度は下がらない。
イベントの形だけでなく、順序、遅延、補償処理の制約も見る。
設計上必要なら、名前、型、意味、アルゴリズム、位置、実行順、タイミング、値、同一性といったコナーセンスの観点で、暗黙の合意を具体化する。
分類名を列挙すること自体をレビューの目的にしない。

## 距離

書籍：8.1〜8.4、pp.146–156。

距離は、一緒に変更するために越える境界と、その調整に必要な労力に関わる。
文、メソッド、オブジェクト、パッケージ、ライブラリ、サービス、システムには異なる境界がある。
モジュール階層では最も近い共通祖先が比較の手がかりとなる。
所有チームや組織、実行時の依存も、実際の調整コストに影響する。

近い配置は共同変更を容易にする一方、無関係なものにも実装、テスト、リリースなどのライフサイクルを共有させる。
遠い配置は独立性を高める一方、共同変更が必要になれば互換性やリリース順序の調整が重くなる。

レビューへの適用：

- ファイルパスに加え、パッケージの公開範囲、依存方向、所有者、テストとリリースの単位を確認する。
- 同一リポジトリだから近い、別サービスだから独立している、と断定しない。採用する評価の粒度をそろえる。
- 非同期通信で実行時の可用性依存を減らせても、移行中の旧新メッセージ形式や処理順序への対応が必要なことがある。
- 距離を縮める提案では、関係する機能だけを移せるかを先に検討する。サービス全体の統合は、無関係な機能を巻き込む可能性がある。

## 変動性

書籍：9.2〜9.5、pp.160–172；11.2、pp.194–197。

変動性は変更の頻度や見込みであり、結合を維持する負担がどれほど現実化するかに関わる。
知識を公開する上流を起点に考え、機能結合では双方を見る。
競争優位のために改善されるコアサブドメインは高変動、支援・汎用サブドメインは比較的低変動という見立てができる。
ただし、事業戦略や依存先が変われば、その見立ても変わる。
低変動の領域でも、高変動の上流へ強く依存すると変更を強制される。これが推定変動性の観点である。

レビューへの適用：

- ドメイン上の役割、今回の変更、予定された変更、履歴の内容を組み合わせる。「コア」という名称だけで高変動としない。
- コミット数には、修正、整形、生成、移動が混ざる。変更を諦めたため履歴が少ないコードもある。対象期間と意味のある変更理由を確認する。
- 同じコミットで編集された事実は共同変更の手がかりにとどめ、同じ業務上の理由や契約変更を追う。
- 上流の変更が、今回共有している知識に影響するかを見る。無関係な内部変更をすべて波及すると数えない。
- 変動性が不明な場合は、頻繁な変更を仮定した結果と、現在確認できる問題を分ける。低変動を根拠に現状維持とするなら、その根拠と再評価条件を示す。

## 均衡の判断

書籍：10.1〜10.2、pp.177–184。

| 強度と距離 | 書籍の見立て | レビューへの適用 |
| --- | --- | --- |
| 強い・近い | 高凝集 | 必要な共同変更を近い範囲に閉じ込めているか。強い結合というだけで分離を勧めない |
| 弱い・遠い | 疎結合 | 独立して変えられるか。境界を越える隠れたルールや順序依存も確認する |
| 強い・遠い | 大域的複雑性 | 波及する変更と調整の負担を確認する。強度を下げるか、関連機能を近づける |
| 弱い・近い | 局所的複雑性 | 関連の薄い機能を一緒に保守する負担を確認する。包含するモジュールの内側を整理する |

高い変動性は二つの複雑性を現実の負担にしやすい。
低い変動性が確認できる場合は、追加の抽象化より現状維持が合理的なこともある。
表は調査の方向を示すもので、配置だけから自動的に違反を生成するルールではない。
分類には、具体的な変更の波及、理解の負担、不要なライフサイクル共有などの証拠を伴わせる。
低い変動性は、既に確認された正しさや契約の違反を正当化しない。

### 数値化を求められた場合

書籍：10.3、pp.184–190。

通常は定性的に報告する。書籍自身も数値評価の主観性を明示している。
数値比較を求められた場合に限り、同じ評価の粒度と尺度を使い、各値の根拠を添える。
本書の1〜10の尺度では、均衡度は `max(abs(強度 - 距離), 10 - 変動性) + 1` で、高いほど均衡しているという見立てになる。
これは工数、障害確率、合否を測定した値ではない。未知の値を埋めて精密な点数に見せない。
`強度 × 距離 × 変動性` だけでは、弱い結合の無関係な機能を近くに集めた局所的複雑性を見落とす。

## 再均衡化

書籍：11.3、pp.197–204；12.4、p.222；13.1〜13.4、pp.226–248。

要件、事業上の役割、チーム構成、配置が変わると、それまで妥当だった境界も見直しが必要になる。
一つの次元を変えたら残る次元を再評価し、下位の境界の改善が上位の複雑性へ変わっていないかも確認する。

レビューへの適用：

| 観察 | 検討する変更 | 確認する代償・条件 |
| --- | --- | --- |
| 内部モデルの変更が遠い利用側へ波及する | 必要な情報へ絞った契約を公開し、所有側で内部モデルから変換する | 変換と互換性維持の負担。元のモデルが安定していれば導入が不要な場合もある |
| 同じ業務ルールを離れた場所で再実装する | 判断を所有する場所へ集約し、必要な結果を共有する | 新たな実行時依存、結果の鮮度、バージョン互換性。共通ライブラリ化だけで更新の協調がなくなるとは限らない |
| 原子的に扱う必要のある機能が分散する | 関係する機能を同じ整合性境界へ移す | 無関係な機能まで統合しない。同期APIによる事前確認だけでは競合を防げない場合がある |
| 機能変更が技術レイヤーやパターン別配置を横断する | 一緒に変わる機能をまとめ、その内側に必要な層を設ける | 既存の公開範囲や所有権。レイヤー構成そのものを違反とせず、共同変更の証拠を使う |
| 無関係な機能が同じクラスやインターフェイスに集まる | 利用目的と変更理由に沿って分割する | 分割後の呼び出しや調整が増えないか。目的や名前の類似だけで凝集を判断しない |
| 強い結合があるが共有知識は安定している | 現状を維持し、再評価の条件を明示する | 新機能、事業戦略、上流の変化、チーム分割で前提が崩れるか |

集約の境界は、参照の便利さやER図の関連だけでなく、実際に守る不変条件から判断する。
メソッド、クラス、機能モジュール、サービスのうち、問題を解ける最小の境界を選ぶ。
書籍の事例を理由に、マイクロサービス、DDD、ポートとアダプター等を全体へ一律に導入しない。
