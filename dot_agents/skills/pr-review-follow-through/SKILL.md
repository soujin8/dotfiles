# PR Review Follow-through

レビュー指摘を一件ずつ事実と照合し、変更の所在と公開状態が分かる形で最後まで追う。指摘を無条件に採用せず、誤解や仕様判断が必要な点も根拠を添えて扱う。

## 1. 対象と到達点を確定する

- PR URL・番号・ブランチ、レビュー対象のスレッド、依頼された到達点を特定する。指定が曖昧なら現在のブランチと対応PRを調べる。対象外のPRや過去の指摘を勝手に広げない。
- `gh` / `gh api` でPRのbase/head、レビュー、インラインコメント、スレッドの解決状態、CI、最新コミットと差分を取得する。画面表示だけや古いローカル差分を唯一の根拠にしない。
- `git status`、ローカルとリモートの差、既存の未コミット変更、スタック構成を確認する。依存PRでは修正を置く層を決める。既存の作業やコミットを保全する。
- 作業範囲が複数の設計判断にまたがる場合は、指摘群、修正先、検証、公開・返信の順序を短く共有する。実装前の整理だけを依頼された場合は、そこで止める。

## 2. 指摘を判定する

各スレッドについて、URL、指摘内容、対象コード、現状、判断、対応先、返信状態を追跡する。判断は次から選ぶ。

- **修正する**: 再現条件、影響、期待動作をコード・テスト・仕様から確認できた。
- **別PR・別層で対応する**: 所有する変更と依存関係を確認し、行き先を明記できた。
- **修正しない**: 指摘の前提が現在のコードや仕様と合わず、根拠を示せる。
- **判断待ち**: 仕様、データ、外部挙動などの決定的な証拠がなく、実装方針を決められない。

変更行だけでなく呼び出し元、既存経路との互換性、非同期処理の失敗・再試行・状態遷移も必要な範囲で追う。指摘の重大さと実データ上の発生有無は分けて述べる。レビューに書かれた案より、確認した問題を直す最小の変更を優先する。

## 3. 修正して限定的に検証する

- 対応が依頼された範囲だけを既存構成に合わせて修正する。仕様判断が未確定の箇所は推測で書き換えず、独立して進められる修正を先に進める。
- テストは設定値の転記や空虚なassertではなく、レビューで問題となった振る舞いを検証する。遅延生成されるfixture、ジョブ投入・通知・CSV生成の有無、例外やリトライ枯渇など、実際の失敗経路に注意する。
- 変更に最も近いテスト、静的解析、型チェックを選び、リポジトリの実行環境・AGENTS.mdに従って実行する。変更が原因の失敗は直して再実行する。文書のみなら内容・リンク・形式を確認する。全体テストを機械的に追加しない。
- `git diff` と `git diff --check` を確認し、指摘への対応と無関係な変更、過剰なコメント、既存挙動の破壊がないか見直す。実行結果と未実行項目を区別する。

## 4. 履歴とスタックを整える

- コミット、リベース、pushの要否は依頼の到達点と既存の許可に従う。対象外の変更を混ぜず、意味のある変更単位でコミットを整理する。履歴を書き換える前に公開済みか、他者の作業に依存するかを確認する。
- スタックでは各変更を所有する層に置く。必要なら下位から上位へリベースし、親子関係、`needsRebase`、作業ツリー、差分を確認する。`gh stack` が使える場合はそのスキルの非対話コマンドと競合回復手順に従う。
- リベース成功をpush成功として扱わない。push後にリモートheadとPR差分を再取得し、意図したコミットが公開されたことを確認する。未pushならその状態を明記し、公開済みの修正として返信しない。
- SHAが変わったら、自分が投稿したレビュー返信中のコミットリンクなどを確認し、旧SHAと新SHAの対応が確実な箇所だけ更新して再取得する。元の説明を保持し、他人のコメントには触れない。

## 5. 返信して状態を確認する

- 返信の投稿やレビュー再依頼が今回の依頼に含まれる場合に実行する。修正を根拠にする返信は、その修正の公開と必要な検証を確認してから投稿する。修正しない指摘への返信は、判断の根拠を確認してから投稿する。案だけの依頼や調査だけの依頼では投稿しない。
- 各スレッドには、採否、変更後の挙動、該当PR・コミット、実施した限定テストを簡潔に書く。修正しない指摘には根拠を示す。別PR対応は対象PRと未完了・完了の状態を明記する。未検証のCIやローカルだけの変更を完了済みと書かない。
- 投稿後にコメントとリンクを再取得し、投稿・編集が反映されたことを確認する。必要ならレビューを再依頼し、その状態も確認する。スレッドの解決操作は、指摘内容と権限・リポジトリ運用に合う場合だけ行う。

## 完了報告

PRごとに、対応済み・見送り・判断待ちの指摘、変更とコミット、限定テストの実行結果、push・返信・再レビュー依頼の実際の状態を短く報告する。ローカルで完了したこととGitHubに反映されたことを分け、残るCIや仕様判断を明記する。
