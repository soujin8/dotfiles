# Sentry Perf Investigation

特定のリクエスト／ページ表示の所要時間を、コード構造の仮説と Sentry APM の実測値を突き合わせて
セクションごとに分解する。独自計測を新設する前に、既存 APM の実測データを一次ソースとして扱う。

## 手順

### 1. スコープ確認（最初に必ず行う）

- 調査対象のフロー（例: リクエスト受信〜レンダリング完了か、作成処理から表示までの全体か）を
  番号付き2択+推奨で確認する。ユーザーは番号のみの短い返答を好むため、選択肢は常に番号付き・推奨案つきにする。
  - 例: 「1. show リクエスト〜レンダリングまで（推奨） / 2. create〜表示までの全体」
- スコープが確定するまで次work手順に進まない。

### 2. 計測データ源の確認

- 独自計測（Benchmark、独自ログ計測など）を提案する前に、必ず「既存の APM（Sentry など）に
  該当データが既にあるか」をユーザーに確認する。既にあるなら、それを一次ソースとして使う。
  自前計測を先に提案しない。
- Sentry へのアクセス方法を確認する。標準は「ユーザーに Sentry Trace Explorer の URL を貼ってもらい、
  claude-in-chrome（ブラウザ操作）で閲覧する」方式。API トークンは使わず、ユーザーのブラウザセッションに
  乗る前提で進める。
  - 想定される URL 形式: `https://<org>.sentry.io/explore/traces/?...&environment=production&query=transaction:<Controller>#<action>&statsPeriod=30d&mode=samples`
  - URL がまだない場合は、対象の transaction（controller#action 相当）を伝えた上で URL の共有を依頼する。

### 3. コード側を先に把握する（Sentry を見る前に）

- Explore サブエージェントを並列起動し、対象リクエストのコードフローを調査させる。
  - ルーティング → controller → service/usecase → 外部API呼び出し → view/シリアライズ
  - background job、キャッシュ、フロント側の描画処理（該当する場合）
- 調査結果から「セクション仮説」を先に立てる。例:
  - before_action 群（認可・前処理）
  - Service/Usecase の初期化
  - 外部API呼び出し
  - 後処理・JSON化/シリアライズ
  - ビュー描画（テンプレートレンダリング）
- この仮説は Sentry の実測と突き合わせるための足場であり、最終報告の区分そのものとは限らない。

### 4. Sentry で実測値を採取する

- claude-in-chrome で Trace Explorer の URL を開き、対象 transaction のサンプル一覧を確認する。
- 個別トレースのサンプルを2件程度開き、span waterfall と breadcrumbs を読み取る。
  - 代表的な指標: db_runtime（DB実行時間）、view_runtime（テンプレート描画時間）、spans.http（外部API呼び出し時間）
  - これらは一例であり、対象スタックの APM が計測する実際のスパン種別・命名に従うこと。
  - 個別スパンの内訳（対象テーブル名、呼び出し先ホスト名など）も採取する。

### 5. 観測可能な単位に再マッピングする

- 手順3のコード仮説のセクションを、手順4で実測できた区分に組み替える。
- 計測されていない区間（コードには存在するが APM 上で個別スパンとして見えない処理）は、
  「全体時間 −（db_runtime + view_runtime + spans.http などの計測済み合計）= 残差」として推計する。
- この残差は必ず「ブラックボックス（未計測）」と明示し、実測値と混同しない。

### 6. 報告する

2段構成で報告する。

**(a) 計測ギャップ提示用の表**

```markdown
| 項目 | 値 | 備考 |
| --- | --- | --- |
| db_runtime | ... | 計測済み |
| view_runtime | ... | 計測済み |
| spans.http | ... | 計測済み、呼び出し先: ... |
| 計測されていない処理（残差） | ... | 推計値。ブラックボックス |
```

**(b) 区分ごとの内訳**

- サンプル間の比較を、可視化ツール（水平スタックバー等）が使える環境ならそれで示す。使えなければ表で示す。
- サンプルのラベルは必ず「Sample 1」「Sample 2」のような匿名表記にする。Sentry 上の実データに含まれる
  エンドユーザー氏名などの個人名を報告に転記しない。

**締めのテキスト（この順で書く）**

1. サンプルから分かったこと（区分ごとの概算%と、サンプル間で変動している要因）
2. 推奨の次アクション（カスタムスパンを追加すべき具体的なメソッド名、改善対象のクエリなど、具体的に）
3. 「この整理でOKか、さらに掘り下げるか」の確認

### 7. 計測ギャップが大きい場合の分岐

残差（ブラックボックス）が全体に対して無視できない割合を占める場合、番号付き選択肢+推奨で分岐を提示する。

- 例: 「1. 既存データだけで一旦整理（推奨） / 2. カスタムスパン追加後に再計測 / 3. 手動 Benchmark 計測」
- このユーザーは基本的に「まず粗くても今すぐ整理する」ことを好み、カスタムスパン追加は次アクションの提案に
  留めて即座には実施しない。ユーザーから明示の希望がない限りこの前提で進める。

## 禁止事項・徹底事項

- 独自計測（Benchmark、独自ログなど）を、既存 APM の有無を確認せずに提案しない。
- サンプルトレースを報告する際、Sentry 上の実データに含まれる個人名（エンドユーザー氏名等）を
  そのまま使わない。必ず「Sample 1 / Sample 2」等の匿名ラベルに置き換える。
- 推計値（残差から算出した値）は、実測値と区別できる形で必ず「推計」「未計測」と明示する。
- スコープ確認・分岐提示は、常に番号付き選択肢+推奨案の形式で行う。
