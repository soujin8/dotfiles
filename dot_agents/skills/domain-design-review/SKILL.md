# Domain Design Review

コードの差分またはファイルを読み、ドメイン知識が適切な概念に閉じ込められているか、手続き的な調整とドメインルールが混ざっていないかをレビューする。

## レビュー前提

- 既存プロジェクトの命名、ディレクトリ構成、アーキテクチャ、テスト方針を先に読む。
- フレームワーク流儀を尊重する。DDD用語を押し付けず、既存の層やクラス名に翻訳して指摘する。
- 仕様が読める場合は、コードより先に仕様・README・テスト・ADR・wikiを確認する。
- 不明な仕様は断定しない。「検討の余地あり」または「確認したい前提」として分ける。
- 差分レビューでは、変更行だけでなく責務判断に必要な周辺コードを読む。

## 責務の基準

### Entity / Aggregate

一意性、ライフサイクル、状態遷移、不変条件を持つドメイン概念を置く。

適切なロジック:
- 自身の状態に対する正当な変更
- 状態遷移の可否判定
- 集約内の整合性ルール
- 子要素を含めた不変条件の保証

不適切なロジック:
- メール送信、外部API、ジョブ投入などの外部I/O
- 複数集約をまたぐ手続き的な調整
- 永続化方式やDBクエリ最適化への直接依存

### Value Object

同一性ではなく値そのものに意味があり、不変で、比較・計算・正規化できる概念を置く。

適切なロジック:
- 値の生成時バリデーション
- ドメイン固有の計算、比較、変換
- 単位、通貨、期間、範囲、識別子形式などの整合性

不適切なロジック:
- DB保存、外部I/O、現在時刻や乱数への直接依存
- 他の集約の状態を読まないと決まらない判断

### Domain Service / Policy / Specification

特定のEntityやValue Objectに自然に属さないが、純粋なドメイン判断として存在するルールを置く。

適切なロジック:
- 複数のドメインオブジェクトを材料にした副作用のない判定
- 資格判定、料金ポリシー、制約判定、照合ルール
- 再利用されるビジネス条件の名前付け

不適切なロジック:
- トランザクション管理
- Repository呼び出しの順序制御
- 通知、決済、外部同期などの副作用の実行

### Application Service / Use Case

ユーザー操作やシステムイベントに応じて、ドメインオブジェクト、Repository、外部Gatewayを調整する。

適切なロジック:
- 入力DTOをドメインに変換する
- Repositoryから集約を取得し、ドメイン操作を呼ぶ
- トランザクション境界を管理する
- 外部I/O、通知、ジョブ投入のタイミングを調整する

不適切なロジック:
- ドメインルールをif文の塊として直接実装する
- Entityの状態を書き換える前に、本来Entityが持つべき不変条件を外側で肩代わりする
- 複数Use Caseから再利用される判断をprivateメソッドに閉じ込める

### Repository / Gateway

永続化や外部システムとの境界を置く。

適切なロジック:
- ドメインオブジェクトの保存・復元
- クエリ条件の組み立て
- 外部APIのプロトコル変換

不適切なロジック:
- ドメイン上の正当性判断
- 状態遷移の可否判定
- 仕様上の例外や代替ルールの決定

### Controller / Handler / Resolver

入出力形式、認可、HTTP・GraphQL・CLIなどのインターフェース都合を扱う。

適切なロジック:
- リクエストのパース
- 認証・認可の入口
- Use Case呼び出し
- レスポンス形式への変換

不適切なロジック:
- ビジネスルール、料金計算、状態遷移
- ドメイン概念の生成ルール
- トランザクションを含む複雑な業務手順

## 検査観点

### 1. ドメイン知識の所在

ビジネスルール、計算、状態遷移、不変条件が、名前のあるドメイン概念に置かれているかを確認する。

検出シグナル:
- Application Service、Controller、Job、Repositoryにドメイン条件のif文が集中している
- 同じ業務条件が複数箇所にコピーされている
- privateメソッド名が業務用語なのに、クラスの責務と一致していない
- テスト名だけに業務ルールが現れ、コード上の概念として表現されていない

### 2. オーケストレーションとドメイン判断の分離

手順の調整と、何が正しいかの判断が混ざっていないかを確認する。

検出シグナル:
- Use CaseがDB取得、状態判定、金額計算、通知文生成、保存を一続きの巨大メソッドで行っている
- Entityが外部サービスやRepositoryを直接呼んでいる
- Domain Serviceが保存や通知まで実行している
- 例外処理やフォールバックがドメイン判断を隠している

### 3. 不変条件と状態遷移の保護

不正な状態が作れない、または作れても境界で検出される設計になっているかを確認する。

検出シグナル:
- setterや公開プロパティで、どの順序でも状態を書き換えられる
- 状態遷移の可否が呼び出し側の事前チェックに依存している
- バリデーションが保存時だけに寄っており、ドメイン操作単位では保証されていない
- enumやステータス文字列に対するdefault分岐が、未知状態を意味のある状態として処理している

### 4. 境界と依存方向

ドメイン層がインフラ、UI、永続化詳細に依存していないかを確認する。

検出シグナル:
- Domain ObjectがHTTP、ORM、Queue、Mailer、Logger、環境変数に直接依存している
- RepositoryがDomain Objectではなく画面用DTOを返している
- Application Serviceより内側の層がController用のエラー形式やレスポンス形式を知っている
- テストでドメインルールを確認するためにDBや外部APIの準備が必須になっている

### 5. 概念の粒度と名前

クラスや関数の名前が業務概念を適切な粒度で表しているかを確認する。

検出シグナル:
- `Manager`, `Helper`, `Util`, `Processor`, `Handler` が業務判断を大量に持っている
- `Service` が単なる計算、Policy、Specification、Value Objectの代用品になっている
- 1つのクラス名に複数の業務目的が混ざっている
- 業務用語ではなく実装手順だけで命名されている

### 6. 仕様外フォールバック

仕様にないデフォルト値、握りつぶし、暗黙補完がドメインの一貫性を壊していないかを確認する。

検出シグナル:
- 例外や不正値をcatchして正常系の値を返している
- 未定義ステータスを勝手に「未処理」「無効」「0円」などへ丸めている
- 外部連携失敗時に、仕様化されていないスタブ値やキャッシュ値で業務処理を進めている
- nullや空文字に業務的な意味を後付けしている

## レビュー手順

1. 対象差分または指定ファイルを読む。
2. 変更の目的、入力、出力、副作用、守るべき不変条件を整理する。
3. 関連するモデル、Use Case、Repository、テスト、仕様ドキュメントを必要最小限読む。
4. 上記の検査観点に沿って、責務のズレを探す。
5. 指摘ごとに「今どこにあるか」「本来どこが責務を持つべきか」「なぜそう判断するか」を明記する。
6. 自信が低いものは断定せず、「検討の余地あり」に分ける。

## 出力フォーマット

レビュー結果は、通常のコードレビューと同じく重大な指摘から先に出す。

```
## Domain Design Review 結果

### 指摘
- **[重要度: High/Medium/Low] [ファイルパス:行番号]** `対象`
  - 現状: [責務がどこに置かれているか]
  - 問題: [なぜドメイン設計上の問題になるか]
  - 提案: [どの概念・層・クラスに移す/閉じ込めるべきか]
  - 根拠: [不変条件、状態遷移、依存方向、再利用性、テスト容易性など]

### 検討の余地あり
- **[ファイルパス:行番号]** `対象`
  - 観察: [断定しきれない構造]
  - 判断材料: [仕様、利用箇所、変更頻度、既存規約など追加で見るべきもの]

### 問題なし
- [確認した観点と、問題なしと判断した理由]

### まとめ
- 検出数: High X件 / Medium Y件 / Low Z件 / 検討 V件
- 総合所見: [責務配置の全体評価]
```

問題がない場合は「問題なし」と明記し、確認した範囲と残るリスクだけを短く書く。

## 重要な原則

- 偽陽性を避ける。単にDDD用語へ置き換えられるだけでは指摘しない。
- 抽象化のための抽象化を勧めない。移動後に不変条件、依存方向、再利用性、テスト容易性のいずれかが実際に改善する場合だけ提案する。
- 既存設計の語彙に合わせる。既存に `UseCase`, `Interactor`, `Command`, `Workflow`, `Policy` などがあるなら、その語彙で提案する。
- ドメイン層を純粋にすることだけを目的化しない。副作用の境界が明確で、業務ルールが追跡可能なら実務上妥当と判断する。
- 指摘は行番号付きで、実装者が次に動ける具体性にする。
