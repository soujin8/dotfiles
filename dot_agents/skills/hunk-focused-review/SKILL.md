# Hunk Focused Review

Hunk の TUI はユーザーが操作する画面であり、agent はセッション daemon を通じて表示範囲とフォーカスを制御する。目的は差分を修正することではなく、読み手が処理の流れを追える単位に分けて意図・依存関係・確認ポイントを説明すること。

## 開始時

1. リポジトリの `AGENTS.md` / `CLAUDE.md` と、差分の理解に必要なプロジェクト文書を読む。
2. `hunk session list --json` で対象リポジトリのライブセッションを探す。
3. セッションがなければ、ユーザーに対象リポジトリで `hunk diff` を起動するよう依頼する。agent は `hunk diff` や `hunk show` を直接実行しない。
4. `hunk session get --repo <repo> --json` で `Repo`、`Path`、`Source`、複数セッションの有無を確認する。
5. `hunk session review --repo <repo> --json` でファイル／hunk構成を先に読む。全体の raw patch が必要な場合に限り `--include-patch` を付ける。

ローカル daemon が sandbox から見えない場合は、同じ `hunk session ...` コマンドを許可付きで再試行する。複数セッションがある場合は、repo root が一致するセッション ID を明示する。

## レビュー単位の作り方

レビュー単位は、読み手が一つの因果関係を追える関連ファイル群とする。目安は 5〜15 ファイル、10〜25 hunks であり、ファイルを一つずつ順番に表示する粒度にも、リポジトリ全体を一度に表示する粒度にも寄せない。

単位の切り方は、差分の責務と依存方向から決める。

- API は、エントリポイント、Serializer または DTO、直接呼び出すドメイン／サービス、対応する request spec をまとめる。
- UI は、入口コンポーネント、直接の子コンポーネント、Store または hook、関連するテストをまとめる。Sidebar のように複数ファイルで一つの表示を構成するものは、Sidebar 内の関連ファイルを同じ単位に含める。
- ドメイン処理は、状態変換を担うモデル／Concern、適用する Service、永続化変更、対応するモデル spec をまとめる。
- 生成物、画像、大量の自動生成差分は、対応する手書きコードの単位から分離し、後回しにする。

まず生成物・大量の自動生成差分を後回しにし、変更の因果関係と依存方向が分かる順に pathspec を絞る。特定の言語やフレームワークの構成を前提にせず、実際の差分から意味単位を組み立てる。

```bash
hunk session reload --repo <repo> -- diff <base> -- <path> <path> ...
```

`reload` では意味単位に属するファイルをまとめて指定する。これにより Hunk のサイドバーには関連ファイル群が残り、読み手は同じ単位の中で依存先を確認できる。フォーカスは集合の入口または代表的な hunk にだけ移し、サイドバーに表示されているファイルへ一つずつ自動的に移動しない。

各単位では、次の順序を守る。

1. `reload` で意味単位に属する関連ファイル群だけを表示する。
2. `review --json` で hunk 数と追加／削除量を確認する。
3. 集合の入口または最初に意味のある代表 hunk へ `hunk session navigate` する。
4. ユーザーが見ている集合を、責務・データフロー・状態遷移の2〜5点に絞って説明する。
5. ユーザーの `次へ` を待ち、同じ集合内の次ファイルではなく、次の意味単位へ `reload` して移る。

同じ意味単位の内部に複数の独立した因果関係がある場合は、単位を分割する。ただし、分割後も関連ファイル群をサイドバーに残し、個別ファイルを一つずつレビュー単位にしない。読み手が特定のファイルや hunk を指定した場合だけ、その箇所へフォーカスを移す。

推奨する基本順序は次のとおり。差分の実際の構成に合わせて単位を統合・分割する。

1. 型・スキーマ・インターフェース・公開契約（存在する場合）
2. エントリポイントと処理のオーケストレーション
3. 中心となるロジック・状態変換・検証
4. 永続化・外部 API・メッセージングなどの副作用とアダプター
5. 起動処理・依存性注入・設定・ルーティングなどの wiring
6. テスト・ドキュメント・生成物

ファイルが複数の責務を含む場合は、関連ファイル群の中で因果関係が分かれる位置を見つけて単位を分ける。hunk の境界だけを理由に、同じ処理の関連ファイルを個別単位へ分解しない。生成物は対応する手書きコードを確認した後に扱い、通常はロジック説明の中心にしない。

新規ファイルは `review --json` の `extra` として現れる。未追跡ファイルを除外する必要がある場合は、ユーザーの意図を確認した上で `diff --exclude-untracked` を使う。

## Hunk 操作

絶対 navigation は、ファイルと hunk／new line／old line のいずれか1つを指定する。

```bash
hunk session navigate --repo <repo> --file <path/to/file> --hunk 1
hunk session navigate --repo <repo> --file <path/to/file> --new-line 120
hunk session context --repo <repo> --json
```

ユーザーコメントを確認する時は、agent コメントと混同しないよう `user` を明示する。

```bash
hunk session comment list --repo <repo> --type user
hunk session navigate --repo <repo> --next-comment
```

コメントには、対象コードの責務と既存設計から読み取れる意図を根拠付きで答える。コード変更やコメント追加はユーザーが明示的に求めた場合だけ行う。レビュー中に自動で全 hunk へコメントを付けない。

## コード変更を依頼された場合

レビュー中にユーザーが修正も依頼した場合だけ、通常の編集手順へ切り替える。

- `apply_patch` で編集し、ユーザーの既存変更を保持する。
- 宣言、参照元、関連テスト、設定や wiring の更新漏れを確認する。
- プロジェクトで定められたフォーマッター・チェッカー・テストを、変更規模と実行コストに応じて実行する。
- 修正後に `hunk session list` でセッションを再確認する。コード変更や TUI 終了でセッションが消えることがあるため、無理に古いセッションを操作せず、必要ならユーザーに `hunk diff` の再起動を依頼する。
- セッションが残っていれば、修正後の差分を `reload` し、レビュー単位とフォーカスを再設定する。

## 説明の観点

単なる差分の読み上げではなく、次を差分に存在する範囲で短く結び付けて説明する。

- どの入口から呼ばれ、どの責務を担うか
- 入力・出力・データ変換がどうつながるか
- 状態変化、エラー、外部 I/O、トランザクション、リトライなどの扱い
- 変更が依存する箇所と、次に読むべきファイル

レビューの最後には、確認済みの単位、未確認の単位、テスト結果、Hunk セッションの現在位置を簡潔にまとめる。
