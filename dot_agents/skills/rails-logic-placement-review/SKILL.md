# Rails Business Logic Placement Review

Railsコードの差分またはファイルを受け取り、ビジネスロジックの配置が適切かを5つの観点でレビューする。
判定基準の理論的背景（なぜサービス/PORO/集約という区別が有効か）は `references/criteria.md` を参照。

## 判定基準（迷ったらこの表で決める）

### サービスクラス vs PORO

| 判定質問 | Yesが多い方 |
|---|---|
| 複数のActiveRecordモデルを横断して操作するか | サービス |
| DB書き込み・外部API呼び出し・メール送信など副作用があるか | サービス |
| トランザクション境界の管理が必要か | サービス |
| 「AしてBしてCする」という手順の調整が主か | サービス |
| 入力から出力を導出するだけ（副作用なし）か | PORO |
| 「Xとは何か」「Xはどう振る舞うか」というドメイン知識の表現か | PORO |
| 状態を持ちその状態に対する操作を提供するか（Value Object的） | PORO |
| 委譲先が1つ以下で、実質は自己完結した計算・判定・変換か | PORO |

判定不能な場合の優先ルール: 副作用の有無を最優先する。副作用が「ない」のにサービスクラスに置かれているなら Service → PORO 推奨の対象。副作用が「ある」のにモデル/POROに置かれているなら Model/PORO → Service 推奨の対象。

### 集約としてPOROに切り出すべきか

以下のいずれかに該当すれば切り出しを検討する。

- 親子関係のモデルで、子の操作時に必ず親の状態チェックが必要
- 複数モデル間の整合性ルール（不変条件）がコールバックやバリデーションに散在している
- `accepts_nested_attributes_for` で複雑なバリデーションをしている
- 「Aを変更するときは必ずBも更新」というルールがコメント等に明記されている
- 1つのフォーム送信で複数テーブルを同時に更新し、途中の不整合がビジネス上の問題になる

以下に該当する場合は切り出さない。

- 単に `has_many` で紐付いているだけで、それぞれ独立して操作可能
- 参照（読み取り）のみの関連、またはeager load目的の関連
- 親子が異なるライフサイクルを持つ（例: UserとOrder — Orderは独立して状態遷移する）

## 検査観点とシグナル

### 1. Service → PORO 推奨
`app/services/` にあるが副作用のないドメイン知識。
- 外部への副作用（DB書き込み・API呼び出し・メール送信等）がない
- `call` メソッド内が自己完結した計算・判定・変換のみ
- 他オブジェクトへの委譲が1つ以下
- 例: `TaxCalculationService`→`TaxCalculator`、`CsvParseService`→`CsvParser`、`EligibilityCheckService`→`EligibilityPolicy`

### 2. Model/PORO → Service 推奨
モデルやPOROにオーケストレーションが混入している。
- モデル内に他モデルの更新や外部サービス呼び出しを含むメソッドがある
- `after_save` / `after_commit` で複雑なオーケストレーションをしている
- POROが複数のActiveRecordモデルを直接 create/update/destroy している
- トランザクションブロックがモデルのメソッド内にある
- 例: `User#create_with_profile_and_send_welcome_email`、`Order#process!` 内で決済・在庫・通知を実行、`after_create :sync_to_external_system, :send_notification, :update_analytics`

### 3. Controller → Model/PORO 推奨
コントローラ、APIコントローラ、serializer、helper、view用privateメソッドにドメイン知識が混入している。
単なるJSONキー名の整形、HTTPステータス制御、薄いDTO詰め替えは対象外。
以下のように「値の意味」「状態の解釈」「派生状態の決定」を知っていないと書けない処理を対象にする。

- privateメソッドがモデル固有の値表現（enum、bitmask、三値状態、初期値、リセット値など）を解釈・変換している
- 保存値、初期値、推奨値、外部分析結果、デフォルト値などの優先順位をコントローラが決めている
- `nil` / `0` / 空配列 / 空文字などの意味づけがモデルや業務ルールに依存している
- 表示用・API用の派生状態を作るために、複数のドメイン概念を組み合わせて判定している
- 同種の値変換、fallback、派生状態構築が複数コントローラやserializerに重複している

提案先は、既存の責務に合わせて選ぶ。
- モデル自身の概念・不変条件ならモデルメソッド
- API表示用・フォーム表示用の派生状態なら ResponseBuilder / FormState / Presenter などのPORO
- 外部I/OやDB更新を伴う手順ならService

### 4. Fat Model 検出
ActiveRecordモデルに埋もれた抽出可能なドメインロジック。
- privateメソッドが目安10個以上
- concernsの中身がモデルの責務と無関係な計算ロジック
- メソッドが `self`（インスタンス属性）を参照せず引数だけで完結する
- `calculate_xxx` / `format_xxx` / `validate_xxx_logic` 系メソッドが多い
- 同じ計算ロジックが複数モデルに重複している

### 5. 集約設計の提案
上記「集約としてPOROに切り出すべきか」の該当シグナルに加え:
- 子モデルのバリデーションが `parent.status` 等の親状態を参照している
- 複数モデルにまたがる計算結果の整合性（例: OrderItemの合計とOrder.total_amountの一致）

提案には必ず次を含める: 集約ルートのクラス名 / 含まれるモデル範囲 / 保証する不変条件 / 永続化の責務（リポジトリ or サービス）。

## レビュー手順

1. **対象の把握**: 差分（`git diff`）またはファイルの変更全体を把握する
2. **プロジェクト構造の確認**: `app/services/`, `app/models/`, `app/domains/` 等の既存ディレクトリ構造・命名規約を確認する
3. **5観点で走査**: 上記の検査観点それぞれについて該当箇所を洗い出す
4. **不明点はコードを読んで確認**: 判断に迷う場合は関連モデル・既存サービス・テストコードを読んで文脈を補う
5. **報告**: 下記フォーマットで出力する

## 重要な原則

- **偽陽性を出さない**: 確信が持てるものだけ報告する。迷ったら「検討の余地あり」に回す。
- **プロジェクトの既存規約を尊重する**: `app/services/`, `app/domains/`, `app/lib/` 等の既存構造があればそれに従う。
- **Railsの定着パターンは二項対立に当てはめない**: Form Object, Query Object, Decorator, Presenter 等に該当する場合はサービス/PORO判定を強制しない。
- **過剰な抽出を勧めない**: 3行程度の計算を切り出すのは過剰。抽出提案は再利用性・テスト容易性・変更頻度の観点で実益があるものに限る。
- **集約の提案は慎重に**: 実際に整合性の問題やコールバック散在が見られる場合のみ。「このトランザクション整合性は本当に必要か」を常に問う。
- **指摘は建設的に**: 「ダメ」で終わらせず、具体的にどのメソッド群をどこに移すかまで提案する。
