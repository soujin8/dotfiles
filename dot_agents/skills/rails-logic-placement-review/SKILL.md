# Rails Business Logic Placement Review

差分または指定コードについて、既存のモデル・サービス・フォーム等の責務に沿って配置を評価する。
ServiceもPOROで実装できるため、ここでの区別はRubyのクラス形式ではなく「処理の調整」と「ドメイン概念」の責務である。

## 責務の判断

| 主な責務 | 配置の候補 |
|---|---|
| 複数モデルや外部I/Oの順序、通知、トランザクションを調整する | Service / Use Case |
| 値の意味、計算、判定、比較、変換を表す | ドメインPORO（Value Object / Policy 等） |
| モデル自身の状態、正当な操作、不変条件を守る | Model、または実益があればドメインPORO |
| 入出力や表示に固有の派生状態を組み立てる | Form Object / ResponseBuilder / Presenter 等 |
| 検索条件や読み取りを組み立てる | 既存のQuery Object等 |

副作用は調整責務を見つける手掛かりにする。副作用があるモデルを一律にServiceへ移す、純粋なServiceを名前だけでPOROへ置き換える、といった判定はしない。
プロジェクトが純粋な計算をドメインPOROに置く、外部連携の調整をServiceに置く等のルールを明示している場合は、その規約に沿って判断する。規約がなければ上記の責務と実益を根拠にする。
背景の判断に迷う場合は [判定基準](references/criteria.md) を読む。

## 集約の判断

集約の抽出は、複数モデル間の不変条件を一つの操作境界で守る必要がある場合に検討する。
親状態が子の操作可否を決める、整合性条件がコールバック・検証に散在する、常に複数レコードを一緒に更新すべき業務ルールがある、といった根拠を確認する。
`accepts_nested_attributes_for` や複数テーブルの更新は調査の手掛かりであり、単独では抽出理由にならない。

単なる has_many、読み取り・eager load、独立したライフサイクルの関連は同一集約にしない。現在のトランザクション境界をそのまま集約境界とみなさず、必要な業務整合性を先に確認する。
提案には集約ルート、含めるモデル、保証する不変条件、永続化の責務を示す。

## 対象に応じた検査と報告

[検査シグナル](references/review-signals.md) のうち、対象に関係する節を使う。
Service内の計算、Model/PORO内の調整、Controllerやserializerのドメイン知識、Fat Model、集約候補を扱う。
Controllerの単なるJSONキー変換・HTTPステータス・薄いDTO変換は対象外とする。

対象と関連コード・仕様・テストから責務と既存規約を確認する。提案は再利用性、検証容易性、変更負担、整合性のどれかに実益があるものに限り、命名・行数・メソッド数だけで抽出を勧めない。
レビューのみの依頼では実装を変更しない。修正も依頼されていれば、修正と必要な検証まで進める。

報告は重要な指摘から、観点、ファイルと行、現状、具体的な問題、移動するメソッド群と移動先、判断根拠を示す。
確度が低いものは判断材料とともに分ける。指摘がなければその旨と確認範囲を短く書き、全観点の空見出しや件数集計は作らない。
