# Rust Web Idiom Review

Rust製webバックエンドの差分またはファイルを読み、「コンパイルは通るが他言語の発想で書かれたRust」を検出する。
中心となる問いは3つ。

- 不変条件は型に乗っているか、それとも実行時チェックと規律に依存しているか
- I/Oの並行性・失敗・キャンセルは設計されているか、それとも成り行きか
- 所有権の流れは意図した設計か、それともコンパイラをなだめた結果か

## レビュー前提

- `Cargo.toml` を先に読み、フレームワーク（axum/actix等）、DBクライアント（sqlx/diesel等）、
  エラー処理（thiserror/anyhow）、バリデーション（garde/validator等）のスタックを把握する。
- 既存プロジェクトの命名、レイヤー構成（handler / usecase / domain / infra 等）、エラー型の階層、
  テスト方針を先に読み、その語彙で指摘する。
- `cargo clippy` が機械的に検出できる項目（`&String` 引数、不要な `clone` の一部、`unwrap` 等）は
  主対象としない。実行可能なら clippy を回して残りに集中する。clippy を実行できなかった場合、
  機械検出可能な項目に気づいたら Low として簡潔に触れてよいが、深追いしない。
  このスキルの主対象は clippy が検出できない設計レベルの判断。
- 差分レビューでは、変更行だけでなく型定義・エラー型・呼び出し元の非同期文脈など、
  判断に必要な周辺コードを読む。
- 不明な仕様・パフォーマンス要件は断定せず「検討の余地あり」に分ける。

## 検査観点

### 1. 型でドメインを表現しているか

不正な状態が「作れない」設計になっているかを確認する。バリデーション関数の有無ではなく、
検証済みであることが型で証明されているかを見る。

検出シグナル:
- ドメイン的な意味を持つ値が `String` / `i64` / `f64` のまま複数の関数を通過している
  （例: `user_id: i64` と `assessment_id: i64` が同じ関数に並ぶ、`latitude: f64` に範囲の保証がない）
- 同一エンティティのIDが場所によって `i64` / `u64` で揺れている
- `bool` 引数・相関する複数の `bool` フィールドが状態機械を隠している
- `kind` フィールド + `Option` ペイロード群の struct（enum で書くべき直和型）
- 自分が定義した enum への `_ =>` ワイルドカード match
- `-1`、空文字、`0` を「値なし」の意味で使っている（`Option<T>` にすべき番兵値）。
  ただしレガシーAPI互換で番兵が仕様になっている場合があるため、断定前に仕様・互換要件を確認する
- バリデーションが `Result<(), E>` を返すだけで、検証済みを証明する型が生まれていない

Rustらしい形: newtype + Smart Constructor（`PostalCode::parse`）、enum によるモデリング
（`ComparisonOutcome::Assessed(..) / Unassessable` のような直和型）、境界で一度 parse したら
下流で再チェックしない（Parse, don't validate）。

### 2. エラー設計

エラーが構造を持ち、境界ごとに適切に変換され、呼び出し側が分岐・リトライ・翻訳できるかを確認する。

検出シグナル:
- `Error(String)` / `Internal(String)` に多種の失敗が流れ込み、呼び出し側が文字列でしか区別できない
- ライブラリ的なモジュール（infra層の個別クライアント等）が `anyhow::Error` を公開している
- リトライ可否・HTTPステータスへの対応が、エラー型ではなく呼び出し側の場当たり分岐で決まる
- `?` だけで文脈が失われ、障害時に「どの操作の何が失敗したか」がログから追えない
- HTTPレスポンスへの変換（`IntoResponse` 等）が散在し、内部エラー詳細がクライアントに漏れる経路がある

Rustらしい形: 失敗の単位ごとに thiserror の enum、リトライ可否は `is_retryable(&self)` のように
エラー型自身の分類として持つ、アプリ最上位でのみ anyhow + `.context()`、
`IntoResponse` は一箇所でステータス対応・ログレベル・詳細マスキングを決める。

### 3. 所有権とデータフロー

`clone` と `Arc` が設計判断として使われているか、コンパイルエラーへの反射か区別する。

検出シグナル:
- 大きな struct / `Vec`（検索結果セット等）を、タスク境界・ジョブ投入のたびに丸ごと `clone` している
- `clone` の理由を「誰が所有すべきか」で説明できない（E0382 を黙らせただけ）
- 読み取り共有で足りるデータに `Arc<Mutex<T>>` を使っている（`Arc<T>` で足りる）
- 保存も変換もしない引数が所有権を取っている（`String` / `Vec<T>` / `PathBuf` 受け → 借用で足りる）
- 関数シグネチャが所有・借用・変更の契約を表していない

Rustらしい形: 借用がデフォルト、複数タスクで共有する大きめの読み取り専用データは
`Arc<[T]>` / `Arc<T>`、`clone` するなら「独立した所有が必要だから」と説明できる。
ただし小さい型・`Copy` 相当・低頻度パスの `clone` は指摘しない（原則の節を参照）。

### 4. 非同期I/Oのオーケストレーション

I/Oが多いwebバックエンドで最も差が出る観点。並行性・ブロッキング・キャンセル・背圧が
設計されているかを確認する。

検出シグナル:
- 互いに依存しない複数のI/O（DB検索、外部API呼び出し）を逐次 `await` している
  → `try_join!` / `join_all` / `JoinSet` で並行化できるか
- `std::sync::Mutex` のガードや DB コネクションを `.await` をまたいで保持している
- `async fn` 内で同期I/O・重いCPU処理（大きなJSONパース、画像処理等）を直接実行している
  → `spawn_blocking` / 専用スレッドの検討
- `tokio::spawn` した fire-and-forget タスクの失敗が観測されず、graceful shutdown からも漏れている
  → `JoinSet` / `TaskTracker`、最低限エラーログとメトリクス
- 外部API呼び出しに timeout・リトライ方針がない、またはリトライが非冪等な操作に付いている
- 無制限チャネル・無制限 spawn で背圧がない（バーストでメモリが伸びる）
- キャンセル（クライアント切断、shutdown）時に中途半端な状態が残る処理が
  トランザクションの外にある

Rustらしい形: 独立I/Oは構造化された並行化、ロックは `.await` をまたがない最小スコープ、
バックグラウンドジョブは bounded チャネル + ワーカープールで背圧と shutdown を設計、
リトライはエラー分類（retryable か）と冪等性に基づく。

### 5. 境界の分離とI/O抽象

ワイヤフォーマットと内部モデルが分離され、I/Oがテスト可能な形で抽象化されているかを確認する。

検出シグナル:
- リクエスト/レスポンス DTO や DBの Row 型が、そのままドメインロジックの引数・戻り値に使われている
- `serde_json::Value` が内部モデルとして流通している
- serde属性・DBカラム順序の都合がドメイン型の形を歪めている
- usecase が具体的なクライアント型（`sqlx::MySqlPool`、`reqwest::Client`）に直接依存し、
  テストで実DBや実APIが必須になっている → trait（port）で抽象化できるか
- 逆に、実装が1つしかなく増える見込みもないI/Oに、ジェネリクス+trait境界が幾重にも重なって
  型シグネチャが読めなくなっている（抽象化のための抽象化）

Rustらしい形: 境界では変換し（DTO → `TryFrom` → ドメイン型）、内部はドメイン型で流す。
I/Oは trait で抽象化しテストではモック実装・wiremock を使う。閉じた選択肢は trait object でなく enum。

### 6. トランザクション境界と整合性

DBトランザクションのスコープと、複数I/Oにまたがる整合性の設計を確認する。

検出シグナル:
- トランザクション内で外部API呼び出しや重い計算を行い、ロック・コネクション保持が長引いている
- 「検索 → 外部API → 保存 → ジョブ投入」の途中失敗時にどの状態で止まるかが設計されていない
  （途中失敗の許容・リカバリ方針がコードからもコメントからも読めない）
- 採番・一意性をアプリ側のチェックだけで守っており、並行リクエストで競合する
  （`FOR UPDATE` / 一意制約 / 楽観ロックの不在）
- リトライされうる処理（ジョブ、外部からの再送）が冪等でない

Rustらしい形: トランザクションはDB書き込みの整合性単位に絞る（外部I/Oは前後に出す）、
競合は DB の機構で守る、非同期ジョブは失敗を状態として記録し再実行可能にする。

## I/Oが多いアプリで特に効くケース集

具体的な before/after のコード例は [references/io-heavy-cases.md](references/io-heavy-cases.md) にある。
指摘を書く前に、該当する観点のケースを読んで「直し方」と「指摘しない条件」を確認すること。
特に観点3（clone）と観点4（async）は偽陽性を出しやすいので必ず参照する。

## レビュー手順

1. `Cargo.toml` とディレクトリ構成を読み、スタックとレイヤー構成を把握する。
2. 対象差分または指定ファイルを読む。変更の目的、入出力、副作用、非同期文脈を整理する。
3. 関連する型定義・エラー型・trait定義・呼び出し元を必要最小限読む。
   ただし clone・所有権の指摘をする場合は例外で、そのデータの最終消費者
   （レスポンス構築、ジョブ、ログ等）を全て特定してから判断する。消費者が1つなら
   move で足り、Arc も clone も不要なことが多い。
4. 可能なら `cargo clippy --all-targets` を実行し、機械検出できる指摘を除外する。
5. 検査観点1〜6に沿って走査する。観点ごとに references/io-heavy-cases.md の該当ケースと照合する。
6. 指摘ごとに「現状」「なぜRustらしくないか」「直し方」「効果」を明記する。
7. パフォーマンス起因の指摘（clone、並行化）は、データサイズ・呼び出し頻度の根拠を添える。
   根拠が取れないものは「検討の余地あり」に分ける。

## 重要度の基準

- **High**: 現時点で誤動作・データ破壊・デッドロック・リソース枯渇の具体的経路がある。
  例: await 越しのロック保持、TX内の外部API、非冪等操作への無条件リトライ、採番競合。
- **Medium**: 今は動くが、構造的に事故を招く。型の保証が欠けていて変更時に壊れやすい、
  エラーが握りつぶされ障害調査ができない、明確なレイテンシ・メモリの無駄がある。
- **Low**: イディオムからの逸脱だが実害の経路が薄い。直すと読みやすさ・保守性が上がる。
- 波及範囲が大きく費用対効果が不明な改善（既存コード全体の newtype 化等）は、
  実バグの兆候がない限り High/Medium にしない。Low または「検討の余地あり」に置く。

レビュー結果は重大な指摘から先に出す。

```

- **[重要度: High/Medium/Low] [ファイルパス:行番号]** `対象`

  - 効果: [コンパイル時保証、並行性、テスト容易性、障害時の挙動など何が良くなるか]

### 検討の余地あり
- **[ファイルパス:行番号]** `対象`
  - 観察: [断定しきれない構造]
  - 判断材料: [データサイズ、呼び出し頻度、仕様、既存規約など追加で確認すべきもの]
  - 提案（任意）: [条件が満たされる場合の直し方]

### 問題なし（Rustらしい点）
- [確認した観点と、良い設計として維持すべき点]

### まとめ
- 検出数: High X件 / Medium Y件 / Low Z件 / 検討 V件

```

問題がない場合は「問題なし」と明記し、確認した範囲と残るリスクだけを短く書く。

## 重要な原則（偽陽性の回避）

- **newtype を全フィールドに勧めない。** 取り違えが実バグになる箇所（複数種のID混在、単位付きの数値、
  検証が必要な文字列）を優先する。単なる表示用文字列まで包ませるのは過剰。
- **clone は悪ではない。** 小さい型、`Copy` 相当、低頻度パスの clone は指摘しない。
  指摘するのはホットパスまたは大きなデータで、かつ `Arc` 化・借用化の受け皿が設計上自然な場合のみ。
- **HTTP境界の実行時バリデーション（garde/validator）は妥当。** それ自体は指摘しない。
  指摘するのは「検証済みの証明が型にならず、下流で再チェックや `unwrap` が発生している」場合。
- **逐次 await が常に悪ではない。** 依存関係がある、DBコネクションプールの同時消費を抑えたい、
  外部APIのレート制限がある、などの理由があり得る。並行化の提案には独立性の確認を添える。
- **レガシー制約（DBカラムが int、Rails互換のSTI文字列等）との変換コードは、**
  enum を source of truth として変換が一箇所に集約されていれば妥当と判断する。
- **抽象化の提案は片方向にしない。** trait 抽象の不足と過剰の両方を見る。移動・抽象化後に
  コンパイル時保証、テスト容易性、障害時の挙動のいずれかが実際に改善する場合だけ提案する。
- 指摘は行番号付きで、実装者が次に動ける具体性にする。
